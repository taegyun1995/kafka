PopupPass / Basic Architecture

선착순 예약의 첫 단일 서버 흐름

Reservation API가 요청을 받고, 같은 서버의 ReservationService가 읽고 · 판단하고 · 쓰는 가장 단순한 방법으로 예약을 처리한 뒤 PostgreSQL에 저장한다. 동시 요청을 대비한 장치는 아직 없다. 먼저 업무 흐름을 단순하게 완성하고, 실제 분리 이유가 생길 때 메시지 브로커와 별도 Worker를 추가한다.

Spring Boot 프로세스 1개 ReservationService PostgreSQL 1개 동기 처리
흐름 시연 화면 열기 → 보호 장치 실행 화면 열기 →

이 문서는 현재 구조를 다룬다. 무엇을 왜 만드는지와 어디까지가 완료인지는 학습 기획에 있다. 실행 코드와 Docker Compose 명령은 backend/README.md에 정리했다. 두 실행 화면 — 흐름 시연과 보호 장치 실행 — 은 모두 실제 서버를 부른다. 서버는 study 프로필로 띄운다.

03

Request Flow

예약 요청 한 건의 이동

처음에는 이 네 단계를 응답과 DB 상태로 확인한다.

  1. 01HTTP 요청 접수사용자가 roundId와 userId에 Idempotency-Key를 붙여 예약을 요청한다.
  2. 02업무 서비스 호출Controller가 회차·사용자·키를 ReservationService에 전달한다.
  3. 03멱등성 확인이미 처리한 키면 새로 판단하지 않고 처음 저장한 결과를 그대로 반환한다.
  4. 04예약 규칙 적용과 저장새 키라면 CONFIRMED 또는 REJECTED 결과를 저장하고 즉시 응답한다.

현재 요청은 같은 서버에서 처리되므로 HTTP 응답 시점에 결과를 확인할 수 있다. request_id는 서버가 만드는 결과 조회용 식별자이고, Idempotency-Key는 클라이언트가 만드는 업무 시도 식별자다. 응답을 받지 못해 같은 키로 다시 보내면 서버는 처음 저장한 결과를 찾아 그대로 돌려준다. 다른 요청에 이미 쓴 키를 재사용하면 409 Conflict다.

멱등성 판정: idempotency_key가 이미 있으면 저장된 결과를 그대로 반환한다. 같은 키를 다른 회차나 사용자에 사용하면 충돌이다. 확정된 예약의 중복 판정은 별도 규칙이며, 현재는 확정 예약이 이미 있는지 애플리케이션이 조회 한 줄로 확인한다. 확정만 보는 이유는 매진으로 거절된 사용자가 자리가 생기면 새 키로 다시 예약할 수 있어야 하기 때문이다.

상태 목록은 schema.sql이 관리한다: Hibernate는 테이블을 처음 만들 때 status의 check 제약을 만들지만, ddl-auto: update는 이미 있는 제약을 고치지 않는다. 상태를 추가하고 옛 제약을 그대로 두면 새 값의 저장이 막히고, 그 위반이 위의 중복 경로로 흘러 엉뚱하게 REJECTED_DUPLICATE로 기록된다. 그래서 상태 목록은 schema.sql에서 매번 다시 만든다.

06

First Milestone

여기까지 먼저 확인

먼저 업무 흐름과 데이터 규칙을 확인하고, 분리의 필요가 생길 때 전송 인프라를 추가한다.

  • HTTP 요청이 올바른 회차와 사용자를 받는다.
  • ReservationService가 정원·중복 규칙을 적용한다.
  • 예약 결과와 남은 수량이 PostgreSQL에 저장된다.
  • 같은 요청의 결과를 조회 API로 다시 확인한다.
  • 회차를 조회하면 남은 자리가 보인다.
  • 마감한 회차는 자리가 남아 있어도 예약을 받지 않고, 그 거절이 매진과 구분된다.
무엇이 이것을 지키는지 직접 본다: 위 목록이 지켜지는 것은 보호 장치 세 겹 덕분이다. 아무 보호도 없는 0단계부터 하나씩 켜며 그때마다 무엇이 깨지는지 보호 장치 실행 화면에서 실제 서버로 눌러 볼 수 있다.
여기까지가 전부다: 위 목록은 요청이 한 번에 하나씩 올 때의 이야기다. 겹쳐 들어오면 정원을 넘겨 팔거나 한 사람이 두 자리를 가져간다. 무엇을 더하면 그것이 막히는지는 보호 장치 실행 화면에서 단계별로 확인하고, 필요를 겪은 뒤에 이 구현으로 하나씩 되가져온다.
