PopupPass / Load

느려지는 지점을 찾는다

지금까지 물은 것은 “답이 맞는가”였다. 초과 예약과 중복 예약은 DB 제약 한 줄로 고칠 수 있었다. 이 화면이 묻는 것은 다른 질문이다 — “제때 대답하는가”. 아무리 정확해도 커넥션 하나는 한 번에 한 건씩만 처리한다는 사실은 그대로 남는다.

처리량 응답 지연 분포 커넥션 풀 대기

브라우저는 한 출처에 커넥션을 여섯 개까지만 연다. 그래서 동시 300건은 화면에서 만들 수 없고 서버 안에서 만든다. 버튼을 누르면 서버가 그만큼의 스레드를 세워 실제 예약 처리를 동시에 호출한다. 정원은 요청 수의 두 배로 잡고 사용자도 전원 다르게 두어 매진·중복 거절이 섞이지 않게 했다. 남는 변수는 시간뿐이다. 현재 동기 프로덕션 경로는 DB 원자적 차감으로 장부를 지키지만, 커넥션을 기다리는 지연은 그대로 남는다.

05

Guarded vs Unguarded

다 고치면 빨라지는가

같은 부하를 보호 없는 코드와 다 켠 코드에 한 번씩 건다. 다른 것은 보호 장치뿐이다.

앞의 초과 예약과 이중 예약은 보호 장치 세 겹으로 막혔다. 그렇다면 그것들을 다 켜면 응답도 빨라지는가. 두 실행은 같은 DB, 같은 커넥션 풀, 같은 재는 방법을 쓴다. 경합을 눈에 보이게 벌리는 학습용 연출(widenRaceWindow)은 양쪽 모두 꺼 둔다 — 켠 채로 재면 재는 것이 코드가 아니라 그 sleep이 된다.

위에서 고른 동시 요청 수를 그대로 쓴다. 두 번 실행하므로 그만큼 걸린다.

눌러 보면 보호 장치가 무엇을 고치고 무엇을 못 고치는지 한 표에 나온다.
