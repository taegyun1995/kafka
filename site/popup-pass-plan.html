PopupPass / Study Plan

기능이 다 되면 Kafka로 옮긴다

이 프로젝트의 목표는 Kafka 학습용 최소 예제다. 선착순 예약을 단일 서버로 끝까지 만들고, 같은 업무를 Kafka와 별도 Worker로 옮겨 무엇이 달라지는지 비교한다. 포트폴리오용 서비스도, 성능 실험대도 아니다.

Kafka 학습용 최소 예제 단일 서버 먼저 기능 완성 후 전환 부하는 근거 확인용

이 문서는 무엇을 왜 만드는가를 정한다. 이 프로젝트의 입구이기도 하므로, 나머지 문서가 각각 무엇을 맡는지 먼저 적어 둔다.

기초 아키텍처 지금 코드가 어떤 구조인가 — 구성 요소 · 요청 흐름 · 테이블 보호 장치 실행 선착순을 무엇이 지키는가 — 실제 서버에 동시 요청을 일으켜 본다 부하 관측 동기 처리가 어디서 느려지는가 — 처리량의 천장, 그리고 보호 장치를 다 켜도 남는 지연 흐름 시연 동기 구현을 실제로 호출한다 — 한 건씩 보낼 때와 겹쳐 보낼 때의 차이 backend/README.md 실행 명령과 API 사용법 — Docker Compose · curl · 테스트
01

Principle

왜 Kafka를 먼저 쓰지 않는가

도구를 먼저 붙이면 그 도구가 푸는 문제를 영영 못 만난다.

Kafka를 처음부터 넣으면 Topic·Partition·Consumer Group 설정을 외우게 된다. 어떤 문제를 푸는 장치인지 겪어본 적이 없으니 설정값의 의미도 남지 않는다.

그래서 순서를 뒤집는다. 먼저 하나의 서버가 HTTP 요청 안에서 예약을 끝까지 처리하게 만든다. 이 구조가 정확히 무엇을 못 하는지 손에 잡힌 뒤에 Kafka를 넣으면, 옵션 하나하나가 앞서 겪은 문제에 대응된다.

이번 기획에서 정한 것: 전환 시점을 부하 수치로 정하지 않는다. 목표가 학습이므로 동기 예약의 업무 규칙과 재시도 안전성이 완성되면 넘어간다. 대신 “완성”의 뜻을 아래 03에서 못 박아, 기능이 무한정 늘어나는 것을 막는다.

다만 왜 큐가 필요한지는 숫자로 한 번 본다. 성능을 끌어올리려는 것이 아니라, 동기 처리가 정확히 무엇을 못 하는지 확인하기 위해서다. 초과 예약은 DB 제약 한 줄로 고쳐지지만, 커넥션 하나가 한 번에 한 건씩만 처리한다는 사실은 그 뒤에도 남는다. 보호 장치를 세 겹 다 켜고 같은 부하를 걸어 보면 차감 유실은 285칸에서 0칸이 되는데 p95 지연은 오히려 40% 늘어난다 — 부하 관측.

03

Definition of Done

“기능이 다 됐다”는 무슨 뜻인가

이 정의가 없으면 1단계가 끝나지 않는다.

기준은 하나다. Kafka 도입 전과 후를 같은 시나리오로 비교할 수 있으면 완료다. 그 시나리오를 먼저 고정한다.

  1. 01회차를 연다정원 2인 예약 회차를 만든다.
  2. 02잔여 수량을 본다아직 2명이 남아 있음을 확인한다.
  3. 033명이 예약한다2명은 확정되고 1명은 매진으로 거절된다.
  4. 04결과와 잔여 수량을 확인한다각자의 결과를 조회하고, 남은 자리가 0이 된 것을 본다.
  5. 05회차를 닫는다마감한 뒤에는 예약을 받지 않는다.

이 다섯 단계를 API만으로 할 수 있으면 1단계가 끝난 것이다. 지금 무엇이 있고 무엇이 없는지 대조하면 이렇다.

기능상태왜 필요한가
회차 생성 있음 POST /reservation-rounds
예약 요청 있음 POST /reservation-rounds/{roundId}/reservations
결과 조회 있음 GET /reservations/{requestId} · 2단계에서 비동기 결과를 확인하는 통로가 된다
회차 조회 있음 GET /reservation-rounds/{roundId} · 잔여 수량이 보이므로 2단계에서 “요청은 받았는데 아직 안 줄었다”는 비동기의 핵심 장면을 보여줄 수 있다
회차 마감 있음 POST /reservation-rounds/{roundId}/close · RoundStatus.CLOSED가 도달 가능해져 예약 전 상태 검사가 의미를 갖는다. 마감은 설정 연산이라 여러 번 호출해도 결과가 같다
결론: 기본 동기 흐름은 끝났고, 이제 동시성 보호 장치를 실제 경로에 반영하는 중이다. 위 다섯 단계가 API만으로 끝까지 돌고, Testcontainers 테스트가 이를 지키는 상태에서 Kafka로 넘어간다. 이 표에 없는 기능은 만들지 않는다(06 참고).
보호 장치를 하나씩 켜 본다: 학습용 코드는 0단계(보호 없음)부터 원자적 차감 → 부분 유니크 인덱스 → 멱등성 키 순으로 무엇이 깨지는지 고정한다. 실제 프로덕션 경로에는 먼저 멱등성 키를 반영했고, 원자적 차감과 부분 유니크 인덱스는 다음 단계다. 같은 것을 실행 화면에서 버튼으로 눌러 볼 수 있다. 요점은 2단계다 — 그 단계가 안전해 보였던 것은 예약이라는 업무의 성질 때문이 아니라 1인 1매 규칙이 멱등성을 대신 제공하고 있었기 때문이고, 규칙을 걷어내면 재시도가 그대로 두 번째 자리를 먹는다. Kafka를 붙이면 at-least-once 재전달이 더해지므로 멱등성 키가 계속 필요하다.
마감을 붙이며 드러난 것: 마감된 회차의 거절을 매진과 구분하려고 REJECTED_ROUND_CLOSED를 더했는데, 이미 만들어진 테이블에는 옛 상태 목록이 담긴 check 제약이 남아 있어 저장이 막혔다. Hibernate는 테이블을 처음 만들 때만 이 제약을 만들고 ddl-auto: update는 기존 제약을 고치지 않는다. 그래서 상태 목록은 schema.sql에서 다시 만든다 — 2단계에서 PENDING을 더할 때 같은 자리를 다시 지나게 된다.

06

Out of Scope

만들지 않는 것

목표가 최소 예제이므로, 안 만들 것을 먼저 적어 둔다.

항목왜 만들지 않는가
팝업스토어 CRUD예약 회차 하나만으로 선착순을 전부 설명할 수 있다. 이름이 PopupPass일 뿐 도메인은 회차 하나로 고정한다
예약 취소Kafka 도입 전후 비교에 필요하지 않다. 자리를 되돌려야 하는 테스트에서는 SQL로 직접 만든다
사용자별 예약 목록requestId로 한 건씩 조회하면 시나리오를 확인하는 데 충분하다
인증 · 인가userId를 본문으로 받는 것으로 충분하다. 선착순 경합과 무관하다
대기열 · 순번Kafka로 옮긴 뒤에 자연스럽게 생기는 주제다. 지금 만들면 비교 대상이 흐려진다
화면 · 프론트엔드사용자용 화면은 만들지 않는다. 흐름 시연과 보호 장치 실행은 API를 그대로 두드리는 학습용 조작판이지 제품 화면이 아니다
이 목록을 늘리고 싶어지면: 그 기능이 03의 다섯 단계 시나리오에 필요한지 먼저 묻는다. 필요하지 않으면 만들지 않는다.
